## 3. 项目库、人工核验与企业关系

- RSS 记录固定为 `kind: lead`、`verification_status: unverified`；关键词阶段只作为提示。正式项目只能来自人工维护的项目 JSON。生成逻辑仅从 `verified` 项目产生规则机会，快照检查拒绝将 RSS 线索标成已核验。
- 项目 ID 和企业 ID 必填且要求唯一。证据必须含 HTTPS 地址、核验观察时间、支持字段和事实摘录；已核验项目还要求核验人、带时区 ISO 8601 的核验时间，并要求声明的字段由证据支持。
- 审计补强了关系 ID 唯一性、关系状态枚举、核验时间格式和已核验关系字段证据校验。未填关系状态按 `pending_review` 处理。
- 目前项目、企业、企业关系和机会数据均为 0 条。因此人工核验规则通过结构和负例测试，但没有真实记录可供逐条审阅；不得把 437 条新闻线索当成已存在的真实项目。

## 5. AI 与机会分析

- 无 API Key 的完整采集运行成功，状态为 `ai_status=disabled`，网站搜索、筛选、项目关系和规则建议流程可用；没有密钥泄漏到生成的数据中（扫描未发现常见 OpenAI/GitHub 密钥格式）。
- 审计前 AI 请求只靠提示词要求 JSON，字段类型校验较弱。已改用 Responses API 的严格 JSON Schema 输出；这符合 OpenAI 对支持模型使用结构化输出的接口形式，但不保证模型事实本身真实。[OpenAI Responses API 结构化输出说明](https://developers.openai.com/api/reference/resources/responses/methods/create)
- 新增输出字段类型检查、候选企业/地点原文匹配，以及摘要/机会理由中的阿拉伯数字证据匹配。AI 只写辅助摘要、候选实体和未核实建议，不写入已核验项目事实字段。
- 仍有残余风险：模型可能用中文数字、未匹配的人名/机构名或非数字表述编造内容；结构化输出保证格式，不保证事实。启用 AI 后仍须抽查结果，维持 `suggested_unverified` 标记，不把 AI 文案作为招标、金额、容量或企业关系的独立证据。
- 规则机会仅对有证据的人工核验项目提出“后续核查方向”，标为 `confidence: low`、`priority: review`。代码没有 0–100 的机会评分，也没有从招标成功率或投资额推算分数。若一期任务书要求数值评分，此项尚未实现；不能将当前优先级标签称作评分。

## 6. GitHub Actions、权限与安全

- 工作流静态检查确认存在 `workflow_dispatch` 手动触发、`main/master` 推送触发、每日 UTC 00/06/12/18 定时任务（菲律宾时间约 08:17/14:17/20:17/02:17，GitHub 可能延迟）。
- 快照提交任务使用 `contents: write`；部署任务使用 `pages: write` 与 `id-token: write`，符合 GitHub Pages 自定义工作流要求。[GitHub Pages 自定义工作流文档](https://docs.github.com/en/pages/getting-started-with-github-pages/using-custom-workflows-with-github-pages)
- `OPENAI_API_KEY` 只作为采集步骤环境变量注入 Python；未写入前端 HTML/JavaScript。没有在仓库真实 Secret 中检查到值（当前还没有 Git 仓库）。
- 构建、校验或部署失败时，GitHub Pages 的上一次成功部署继续服务；现在所有数据源同时失败会让构建标红并跳过部署。部分源成功仍可发布带有失败状态的快照，旧线索保留。
- 第三方 Actions 目前用版本标签引用而非完整提交 SHA 固定；建议上线前按组织供应链策略决定是否固定 SHA 并定期升级。分支保护必须允许 workflow bot 推送快照，否则持久化步骤会失败并阻止该轮部署。

## 7. 已修复的问题

1. RFC 822 RSS 发布时间按字符串排序可能错序；改为解析时间戳后按真实时间排序，并对无法解析的发布时间回退到 `observed_at`。
2. Google News 返回的 `Untitled` CMS 占位记录污染新闻线索；解析与历史合并阶段均过滤此类标题。
3. AI 输出原先没有严格 JSON Schema 与稳健字段类型校验；已增加严格结构化输出和基本数字/实体来源约束。
4. 关系 ID、关系核验状态和带时区核验时间校验不足；已补强并增加负例测试。
5. 全源失败及配置异常此前会以退出码 0 结束；改为非零码，避免 Actions 误报成功并部署错误状态数据。
6. 增加全源失败保留历史、AI 无密钥、AI结构和证据约束、RSS 占位标题、时间排序、关系校验及退出码测试。

1. 确认是否接受“仅标准底图地名、没有三大区域图层”以及“没有数值机会评分”的现状；若不接受，先补齐再重新运行本审计中的地图/机会检查。

3. 在仓库 Settings → Actions → General 启用 workflow 所需的读写内容权限；如 `main` 有分支保护，允许 Actions bot 更新 `site/data/data.json`，或调整保护规则以支持该自动提交。
4. 在 Settings → Pages 选择通过 GitHub Actions 部署。首次运行会建立/使用 `github-pages` 环境。
5. OpenAI Key 为可选项。不用 AI 就不添加 Secret；启用时把 Key 存在仓库 Actions Secret `OPENAI_API_KEY`，不要写入源码、提交记录或 Pages 文件。可选模型放在 `OPENAI_MODEL` 仓库变量中。

7. 打开 Actions 输出的 Pages 地址，检查六个页面、数据时间、源链接、无坐标提示、地图署名及手机布局。人工点击核对重点线索的来源原文，不把 RSS 新闻自动升级为项目。
8. 定时运行按 UTC 00/06/12/18 执行；GitHub 定时任务可能延迟。上线首周每天查看 workflow 状态、source health 和失败日志，再决定是否缩短或调整采集频率。
