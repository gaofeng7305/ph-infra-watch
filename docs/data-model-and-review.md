# Data model and human review guide

The JSON files in `config/` are the editable source of human-maintained records. No project, company or opportunity is included by default. Add a record only after locating a public source that supports it.

## News leads

`site/data/data.json` is generated by `scripts/collect.py`. Each RSS result has `kind: "lead"` and `verification_status: "unverified"`. A keyword such as “tender” is saved only as a `stage_hint`; it does not mean an open tender exists. AI extracted names and places are candidates and remain unverified.

## Projects

Edit `config/manual_projects.json`:

```json
{
  "projects": []
}
```

Each project record should include:

| Field | Meaning |
|---|---|
| `project_id` | Stable unique identifier, for example an internal `prj-...` ID. |
| `name` | Name shown on the site, matching a cited source where possible. |
| `sector` | `energy`, `telecommunications`, `cross_sector` or `general`. |
| `stage` | A human-reviewed stage label. Use `null` if not established. |
| `province`, `region` | Location as supported by evidence. |
| `island_group` | Optional `Luzon`, `Visayas` or `Mindanao`; include only when a source supports the assignment. Used for map filtering and counts. |
| `coordinates` | Optional `{ "lat": number, "lon": number }`; use only reliable coordinates and include `coordinates` in the source evidence `supports_fields`. |
| `capacity`, `budget` | Optional objects with value and unit/currency. Leave `null` if undisclosed. |
| `owner`, `developer`, `contractors` | Optional names; each claim needs supporting evidence. |
| `verification_status` | `pending_review`, `verified` or `needs_review`. |
| `evidence` | One or more source records; see below. |
| `verified_by`, `verified_at` | Required when status is `verified`; use a reviewer name/role and ISO 8601 timestamp. |
| `change_history` | Optional chronological list of changes, including prior value, new value, evidence and review time. |

Evidence object:

```json
{
  "url": "https://official.example/path-to-source",
  "source_name": "Publisher or agency",
  "published_at": null,
  "observed_at": "2026-11-03T00:00:00Z",
  "quote_or_fact": "Short paraphrase of the supported statement",
  "supports_fields": ["name", "stage"]
}
```

The URL above is a format illustration only, not a real project source. Replace it before adding a record. Every evidence URL must use HTTPS. `observed_at` records when the curator checked the source; it is distinct from the source publication time. `supports_fields` must list the fields this evidence supports.

## Companies and relationships

`config/manual_companies.json` contains companies with a stable `company_id`, `name`, optional `aliases`, `entity_type`, optional `country`/`website`, `verification_status` and `evidence`. A website is optional and must use HTTPS if included.

`config/manual_relationships.json` contains rows with:

- `relationship_id`
- `company_id` and `project_id` referring to existing records
- `role`: `owner`, `developer`, `epc`, `operator`, `supplier`, `investor` or `unknown`
- optional `verification_status`
- `evidence`

Do not merge similarly named entities unless evidence establishes they are the same organization. A relationship is its own claim and requires evidence, even when both entities exist.

## Opportunities

`config/manual_opportunities.json` is for curated opportunities. Include `opportunity_id`, `title`, `opportunity_type`, optional `project_id`, optional `company_ids`, `rationale`, `risks`, `next_checks`, `evidence`, and a `verification_status`. Verified opportunities also require `verified_by` and `verified_at`.

The rules engine creates low-priority, `suggested_unverified` research directions only from human-verified projects with evidence. Each opportunity receives a 0–100 follow-up priority score: evidence completeness (35), demand clarity (30), stage/procurement relevance (20), and freshness (15). Fewer than two source URLs caps the score at 45; without a verified project record it is capped at 30. The score is not project truth or deal probability. The score is recalculated during collection and records its update time and dimension reasons.

Optional AI may draft a summary, candidate entities/locations, rationale, risks and next checks. Candidate entities/locations must appear in source title/summary and carry a source link. AI schemas do not include amount, capacity or procurement fact fields; the snapshot validator rejects unsupported extra fact fields. AI output never changes a verification status. A human must verify claims against original sources.

## Review procedure

1. Read the original public source and record the exact source URL and observation time.
2. Enter a project with `pending_review`, or keep the information as an unverified news lead. For bulk entry see [data-import.md](data-import.md); imports are appended as `pending_review`.
3. For each field, list evidence that directly supports it. Record conflicting or unavailable information as unknown rather than filling a guess.
4. Run `python scripts/validate_data.py` and `python scripts/check_snapshot.py`.
5. A reviewer checks the source again, then sets `verified`, `verified_by`, and `verified_at` only for supported facts. If a source becomes stale or contradictory, set `needs_review` and update its history.
6. Commit the JSON change. GitHub Actions validates it, combines it with discovered leads, and publishes the static site.
